## Release checks by tier (v206)

The user wants Midnight Siege (the mansion) and Dead Tide held to the same rule: treat any measurable regression in either mode as an issue to correct before release. How much measuring that takes depends on what a change touches, decided for each mode on its own by `scripts/release-tier.mjs`:

- **Run it on every release:** `node scripts/release-tier.mjs` shows each mode's tier and why; `node scripts/release-tier.mjs --measure` makes the measurements its tiers call for, beside `origin/main`. It reads which files changed (a new version number alone is not a change) and which mode loads each one: the mansion (`index.html`, `siege.html`), Dead Tide (`tide.html`) and the mode picker (`modes.html`). A shared module counts for every mode that loads it.
- **Quick:** nothing that mode loads changed. No performance runs for it; the tier report is the proof that its files are main's.
- **Standard:** something it loads changed. The script measures one load of each build side by side (files and bytes, shader programs, geometries, textures, draw calls and triangles in every fixed view and the mansion's fight, memory, load phases), a short frame-logic series, and each mode's golden trace (the mansion's `scripts/golden-trace.mjs`, Dead Tide's `scripts/tide-golden-trace.mjs`). No difference is the proof.
- **Full:** the standard comparison found a difference, so the script runs that mode's whole protocol: two full measured pairs, 40 balanced load-phase runs and 24 frame-logic pairs. Investigate and correct any regression it reports before release, as the mansion's rule has always required.
- **Always:** run `npm test` whatever the tiers. Report each mode's tier, with its numbers, in the summary and the pull request. Commit the full protocol's results to `perf/` (`perf/README.md` lists them); standard results can stay in `.tier/`.
- **Escalate by hand when in doubt:** `--measure --full` runs the full protocol for every mode that changed. Do so when the user asks, or when a change could cost something these measures cannot see (for example work that only happens later in a run).
- **Keep the map right:** if the report says a file was "fetched but missing from the tier map", fix `refsOf` in the script before trusting its tiers. Dead Tide's golden trace covers the island without enemies (walking, Radio Hill and the shack, wading, every gun, the katana, grenades, death and the session); when its enemies come ashore, add a fight scenario to it and to its frame logic (`scripts/frame-logic.mjs --mode tide`). A change meant to leave the island as it was must keep its existing scenarios byte-identical.

## Gameplay quality and implementation judgment

- **Implement the intent, not just the literal request.** Treat user instructions as descriptions of intended outcomes. Make reasonable, context-aware design decisions to produce complete, functional results without requiring the user to specify every obvious detail.
- **Validate gameplay usability.** When adding or modifying environments, check player dimensions, camera clearance, walkable surfaces, collision geometry, stair accessibility, enemy navigation, and interaction reach wherever applicable. A feature is not complete merely because its geometry or code exists.
- **Maintain believable proportions.** Environmental additions must use appropriate scale relative to the player and existing architecture. For example, new floors must provide adequate headroom and usable navigation space.
- **Preserve existing gameplay systems.** Consider how each change affects combat, AI, progression, economy, interactable objects, multiplayer-adjacent systems such as shared leaderboards, and performance. Avoid unintended changes to unrelated mechanics.
- **Respect the performance budget.** Prefer efficient geometry, reusable materials, optimized effects, and lightweight implementations. Avoid unnecessary draw calls, expensive shader operations, or excessive per-frame calculations.
- **Maintain visual and mechanical consistency.** New features should match the established atmosphere, architectural style, weapon behavior, feedback systems, and overall design language of Blackthorn.
- **Perform a self-review before completion.** Check whether the implementation fulfills the user's actual gameplay intent, not merely the wording of the instruction. Look for obvious usability problems, broken interactions, regressions, and missing edge cases. Fix issues discovered during review.
- **Distinguish verified results from assumptions.** Do not claim visual quality, frame-rate performance, or gameplay feel has been verified unless those aspects were actually tested. When browser rendering or interactive testing is unavailable, clearly identify the limitation.
- **Be proactive but stay within scope.** Correct obvious issues directly related to the requested change. Avoid unrelated redesigns, speculative features, or major architectural changes without explicit authorization.
